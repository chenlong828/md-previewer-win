# 开发执行纪律：动手到交付

设计解决「做成什么样」，执行纪律解决「做的过程不跑偏、交付可验证、不出事故」。分工：**req-scenario-spec** 管需求、场景与任务拆分，**design-before-coding** 管动手前怎么想，**arch-design-spec** 管架构怎么定，**doc-layout-spec** 管文档放哪，本 skill 管动手到交付怎么干。

## 零、不确定就问，不自行发挥

默认值只在「选错不影响结构、可逆」时直接采用。遇到以下任一情况，停下来提问，给 2–3 个选项和推荐，一次问清：

- 规则没覆盖，或两条规则冲突；
- 选择会改契约、数据结构、组件边界、目录结构；
- 需求本身有歧义，两种理解都说得通；
- 要删除或覆盖已有内容。

不满足以上且规则有默认值的，按默认执行，并在收口记录写明用了哪个默认。禁止「默默选一个然后继续做」。

## 一、规则分层：先硬拦截，再自律

能用脚本、schema、测试、hook 或硬拦截保证的，不交给模型自律。每条规则落地前先问：它能不能变成 lint、pre-commit、CI 门禁或审批弹窗？能自动化的优先自动化，剩下的才是纪律。

| 规则 | 硬拦截手段 |
|---|---|
| 密钥不入库 | pre-commit secret 扫描（gitleaks 类）+ `.gitignore` + commit-msg 检查 |
| fallback 掩盖业务字段 | lint 自定义规则（如 ESLint `no-restricted-syntax`），匹配空值兜底写法 |
| 提交前过目 diff | pre-commit hook 输出 staged diff |
| 高危命令确认 | 执行环境的审批机制 + 受保护分支 |
| 测试有效性 | CI 断言统计 + CR 清单（难全自动） |
| 一个 commit 一件事 | 难自动化：本 skill 纪律 + CR |

## 二、工作方式

- **任务 = 一个对话 = 一次交付**：开工先查目标组件有没有在飞任务（组件级 WIP=1），再读 `brief.md` 的任务表与装载清单；收工更新任务状态、一句结论和未决问题。commit 只在任务完成时产生，绑定 `T-` 与 `SCN-`。
- **一次任务只动一个组件**：改动范围 = 该组件源码 + 该组件规格 + 本任务场景文档 + 测试；顺手看到的东西记待办，不进本次 diff。
- **先批量理解，再直接实现，最后集中验证和汇报**：动手前把该读的一次读完——同类实现、调用链、既有约定；实现阶段不边读边猜；验证阶段一次验完所有验收场景再汇报，不挤牙膏式边做边报。
- **动工前核对改动级别与确认门**：定级与人工门由 arch-design-spec 判定——P1 未确认不编码，P2 未确认不合并，P0 不写实现代码；核对未过就停在设计与确认，不抢先动手。
- **修改前先找同类实现和现有命名风格**：先读同目录、同层的既有实现，跟随既有风格与命名，不引入第二套写法；仓库里已有解决同类问题的代码，先复用或仿写，不另起炉灶。
- **diff 聚焦**：每一行 diff 都对应当前任务目标、缺陷修复或验证需要。不顺手升级依赖，不做无关重构，不删除用户已有改动；看到要顺手改的东西，记进待办或提出建议，不混进本次 diff。
- **单一事实来源**：提示词、配置、常量、接口和文档不要重复定义；同一事实只保留一个来源，其他地方引用（文档树内的「一处一事」见 doc-layout-spec）。

## 三、验收

- **任务三件套**：目标、非目标、影响场景，定义与维护在需求卡与场景卡（req-scenario-spec）；这里只核对，不全。
- **验收以场景测试为准**：每个场景 3 正例 + 1 反例，断言具体的值、状态或行为；禁止只检查 `toBeDefined()`、`toBeTruthy()` 这类存在性断言。`skip` 必须有替身（harness/像素探针/人工记录）并登记，否则该场景不能标 `verified`。
- **修 bug 的固定顺序**：先写最小复现或测试 → 复现变红 → 修复 → 验证通过（变绿）。没有复现的修复无法证明修对了，也无法防止复发。
- **测试必须验证具体业务结果**：一条测试说不出「它验证了哪条业务规则」，就是废测试。
- **分类型验收清单**：
  - **UI 任务**：桌面与移动端关键视口都验证；检查文字溢出、元素遮挡、安全区、交互状态（悬停/禁用/加载/空态/错误态）。
  - **数据/内容任务**：给出样例输入、样例输出和失败样例；空值与边界值必须覆盖。
  - **发布/打包任务**：必须有 dry-run 或 checklist；产物可追溯（版本号、构建号、变更清单）。
- **交付前裁决**：合并 / 发布 / 冻结前，按 `arch-design-spec` 第 8 步的四档输出 `works/<工序>/review.md`；本 skill 不重复定义档位，P3 免写（见该步按定级裁剪）。
- **合并门**：blocker 必须清零；decision 必须已落文档与 pinning test；hold 必须已转出并写明不阻塞理由。
- **裁决摘要**：result.md 记一行，如「blocker 0 / decision 2（已落测试）/ hold 1（已转待办）」。

## 四、错误处理

- **不用 fallback 掩盖业务数据**：`value ?? 0`、`name || "Unknown"` 这类兜底只允许用于真正可缺省的展示性字段；业务数据为空是缺陷，让它暴露出来，不要编一个默认值糊过去。
- **业务逻辑层不吞错**：不滥用 try/catch；让错误自然暴露，只在 API、任务或命令入口边界统一处理。
- **改输入校验前先列变体**：把真实输入变体和边界值列全（合法、空、null、超长、非法格式、并发重复、极端数值），再改实现；这份清单就是校验的测试用例。

## 五、安全边界

- **权威清单在常驻层**：密钥禁区、提交前敏感信息检查、高危操作确认清单，以全局 AGENTS.md「安全与确认边界」为唯一权威——常驻生效，不依赖本 skill 加载。
- **密钥执行细则**：示例配置一律用占位符；`.env`、日志、截图、导出数据在 add/commit 前过一遍；`git status` 里出现未忽略的 `.env` 或含密钥文件，先处理再继续。
- **硬拦截优先**：能装 pre-commit secret 扫描就装，扫描命中比记忆可靠（手段见第一节表格）。

## 六、工作区卫生

- **交付前**：`git status` 清点全部改动，确认每处改动都属于本任务；出现计划外的改动，先弄清来源再决定保留或还原。
- **提交前**：`git diff` 或 `git diff --cached` 逐块过目，确认没有调试残留、密钥和无关文件。
- **一个 commit 只做一件事**：feature、fix、格式化、无关清理分开提交；混合提交无法回溯、无法回滚。
- **任务表随任务状态更新**；收口的 `result.md` 写结论落点，不写流水账。
- **临时文件归位**：项目内临时文件放项目约定目录，不在仓库根目录散落一次性文件；过程文档归 doc-layout-spec 管辖的目录。

## 七、失败信号

出现任何一条，停下来纠正再继续：

- 一个 commit/PR 里混着功能、格式化和依赖升级。
- 测试里全是 `toBeDefined()`、`toBeTruthy()`，说不出验证了哪条业务规则。
- 业务代码里用 `?? 0`、`|| "Unknown"` 兜底不该为空的字段。
- try/catch 吞掉异常只打个 log，主流程若无其事继续。
- `git status` 里躺着未忽略的 `.env` 或含密钥文件。
- 仓库根目录多了 `test1.txt`、`tmp.js` 这类一次性文件。
- 同一个组件有两个在飞任务。
- 场景标 `verified`，但有 skip 无替身。
- 规则没覆盖，却自己默认了一个做法。
- 汇报说「应该可以」，但没有任何一个验收场景真的跑过。
- 为了让测试通过改了断言，而不是查了实现。
