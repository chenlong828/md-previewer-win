# 架构设计规格：模块、依赖、契约与冷热路径

架构规格不是组件清单，而是一组可检查的约束：模块为什么存在、依赖允许指向哪里、契约承诺什么、热路径允许经过谁、数据由谁写、每块如何验证、这次改动由谁拍板。缺任何一项，架构会在第一次跨模块需求时腐化。它不替代详细设计：类图、时序、算法与具体框架用法，在架构规格冻结后再展开。

本 skill 与其余四个 skill 的分工：

- **req-scenario-spec**：负责需求卡、业务功能树、场景卡与任务拆分；本 skill 只消费场景里的组件与不可变引用，不重复需求流程。
- **design-before-coding**：负责从业务问题到组件级修改方案的通用设计流程；本 skill 是其架构规格层，负责组件/模块切分、分层依赖、契约、冷热路径、数据所有权、验证计划、预算与定级。
- **dev-execution-spec**：负责编码执行、验收与提交纪律；本 skill 定下的改动级别与人工确认门（P1 未确认不编码、P2 未确认不合并）在它那里作为动工前置核对。
- **doc-layout-spec**：负责这些产物放在哪里；本 skill 只决定内容与判据。组件规格落到 `design/components/<id>/spec.md`，场景落到 `design/scenarios/`，过程文件落到 `works/<工序>/`，决策落到 `history/decisions/`。

## 〇、组件、模块与执行器

本 skill 的架构单元只有三种，先分清再谈切分：

| 单元 | 定义 | 判据 |
|---|---|---|
| **组件** | 有行为、有契约、有独立验证入口的最小单元 | 只加载它的源码 + 规格 + 测试，能跑通自己的验证 |
| **模块** | 带门面的组合组件，内部由若干组件构成 | 对外只暴露门面能力；只用于顶层 1–2 层；跨模块只走门面 |
| **执行器** | 基础层的通用编排原语（并发/串行/fan-in/fan-out/超时/补偿） | 删掉全部业务组件后仍能编译、跑测试；能原样搬到别的项目 |

**KISS 是组件切分的第一原则**：一个组件只做一件事；能用更简单的结构满足当前需求，就不引入抽象、分层或模式。切分的细分原则随实践沉淀，本版只定这一条主原则与下面的模块卡。

**组件状态**：`planned`（只有职责与契约，无代码/测试）→ `active` → `retired`。新增组件、改模块边界、改组件归属都按 P1 处理；`planned` 由设计任务产出，`change` 任务落地后转 `active`。

**预算**：单组件 ≤120k token（源码 + 规格 + 测试，按字节折算），单任务装载 ≤250k。KISS 是实际约束，120k 只是上限；超限先拆组件或拆任务，不靠“小心一点”维持。

**术语**：下文沿用「模块」一词；凡未特指组合模块时，按组件理解，两者规则相同，差别只在门面与所处层级。

## 一、核心判据

1. **业务能力先于结构**：业务模块必须拥有一个业务能力、业务规则或业务数据；只做接口包装和机械转发的模块没有存在价值。技术边界模块（防腐层、适配器、仓储）可以薄，但价值是隔离、稳定或策略，不是“转发”。
2. **变化轴定边界**：一个模块封住一个易变的设计决策。最可能变化的轴（渠道、格式、规则、流程、规模、外部系统）应当只改一个模块。
3. **契约是唯一相识面**：契约 = 签名 + 不变量 + 错误模式。契约里只出现稳定概念，框架、SDK、ORM、HTTP、数据库类型一律不外漏。
4. **依赖指向稳定**：调用向下，源码依赖指向抽象或稳定侧；具体实现只在组合根出现。易变依赖稳定，具体依赖抽象。
5. **数据单家、状态显式**：共享业务数据只有一个写入口；请求级状态由 context 显式携带；模块没有隐藏的可变业务状态，重启后与并发双跑时行为一致。
6. **冷热分路**：热路径最小依赖、严格失败语义、资源隔离；冷路径异步、可重试、可暂停、最终一致。冷活不得内联进热路径。
7. **复杂度有预算**：每引入一个模块、抽象或依赖，都要说清它换来了什么；说不清收益的，删除或合并。
8. **人工门与风险相称**：P3 自动测试；P2 人最终确认；P1 人参与设计；P0 人共同决策。不把 P1 当 P3 做，也不把 P3 套上 P1 的流程。

## 二、分级与人工确认门

先定级，再决定设计重量。级别按「本次改动」判定，不按整个系统；判定不清时向上取一级。

### 判定顺序

1. 业务目标、数据权属、关键约束能否说清？不能 → **P0**。
2. 是否触碰模块切分/合并、核心契约、核心 schema、数据所有权、分层依赖或热路径架构？是 → **P1**。
3. 是否实质性跨文件或跨模块、改非核心数据库/内存表字段、新增内部依赖/适配器、做兼容性契约变更？是 → **P2**。
4. 是否单模块局部、无公共契约/schema/依赖/热路径行为变更、自动化测试可覆盖？是 → **P3**。
5. 仍不确定 → 按更高一级。

### 级别表

| 级别 | 触发条件（任一） | 设计动作 | 人工门 | 最小产物 |
|---|---|---|---|---|
| **P3** | 单模块内部局部实现；不改公共契约、数据库/内存表 schema、依赖关系、热路径行为；通常单文件或纯机械多文件（重命名、格式化、测试同步）；自动化测试可覆盖 | 轻量变更说明；确认模块卡不变；补契约测试/回归测试 | 自动化测试 + 常规代码评审 | 变更说明（含影响面与测试） |
| **P2** | 非核心数据库/内存表/持久化 schema 字段变更；实质性跨文件或跨模块调整；新增内部依赖/适配器；兼容性契约变更；非核心配置/批处理调整；热路径局部优化但不改契约、依赖、资源隔离 | 影响分析；契约 diff；迁移/回滚方案；测试计划 | 人最终确认，可异步；设计可由 agent 完成 | 影响规格（1–2 页）+ 确认记录 |
| **P1** | 模块切分/合并；新增业务模块；核心契约、核心 schema、数据所有权、分层依赖变更；热路径的依赖、资源隔离、失败语义或一致性边界变更；跨团队/高爆炸半径/不可逆迁移；扇出超限，或扇入进入平台级（6+） | 完整架构规格；候选方案与权衡；评审走查 | 人参与模块切分与契约定义 + 最终确认；设计冻结后才编码 | 架构规格 + 决策记录 + 确认记录 |
| **P0** | 业务目标/数据权属/关键约束说不清；需求冲突；无可行架构；重大未知（遗留系统行为、合规、跨组织依赖） | 停止设计与编码；列已知/未知、选项与代价 | 人共同参与决策 | 阻塞简报 |

### 定级纪律

- 判不准往上取：P3 → P2，P2 → P1。
- 触碰 P1 触发项即 P1，不因“改动很小”降级。
- **核心** = 收入、关键用户旅程、安全合规、不可逆、多租户隔离；模糊时按核心处理。
- P3 不含任何 schema、公共契约、新依赖、热路径行为变更；含任一即至少 P2。
- 新增组件、改模块边界、改组件归属按 P1；结构决策（组件/模块/分层/编排归属）必须给 ≥2 个候选与否决理由，人确认后落。
- 升级随时可做；降级必须重新定级并记录理由；P1/P2 已确认后降级需人确认。
- P0 不写实现代码；P1 未确认不写实现代码；P2 未确认不合并。
- P2 的“人最终确认”是落地前签字，不是设计时陪跑；P1 的人参与必须发生在切分与契约阶段，不是最后补签。

## 三、工作流

### 第 1 步：盘点业务能力与变化轴

先不要画模块，先列能力。能力是业务动词，不是技术动作（“下单”是能力，“发 HTTP 请求”不是）。

| 能力 | 服务对象 | 触发 | 结果 | 规则/不变量 | 数据 | 失败语义 | 频率/时效 | 核心? | 冷/热 | 变化可能性 |
|---|---|---|---|---|---|---|---|---|---|---|

- 标出 **3 个最可能变化的轴**、**3 个最不能破的不变量**、**3 个最痛失败**。它们分别决定模块边界、契约和验证重点。
- 核心/非核心、冷/热先粗标，后续可修正，但必须显式记录。
- 业务方说不清时，标记为 P0/P1 的开放问题，不用技术假设填空。

### 第 2 步：切分模块

从业务能力到候选模块，不按 controller/service/repository 切，也不按文件大小切。**先用 KISS 切出原子组件（一个组件只做一件事），再在顶层 1–2 层用模块（带门面的组合组件）收口；跨模块只走门面。** 高内聚看变化：同一条业务规则变化时，一起改的元素应住在同一个模块；低耦合看相识：模块之间只通过契约，不窥探彼此内部；信息隐藏看决策：每个模块只封一个易变决策，契约里不出现这个决策的实现细节。每个候选模块写一张模块卡（模板见第五节），然后逐项过以下测试：

1. **一句话测试**：能说清“负责 X，不负责 Y”。说不清 Y 时，Y 就是下一个模块的切分点；职责句中出现“和/以及/同时”并列多个业务能力，是拆分信号。
2. **变化测试**：改一条业务规则，需要改几个模块？答案应为 1（最多再加契约）。跨多个模块同步改，说明边界切错。
3. **数据测试**：这份业务数据有几个写入口？只能有 1 个写入口。多个写入口 → 提取数据服务模块。
4. **价值测试**：删掉这个模块，消失的是业务能力、业务规则、数据所有权或边界保证，还是仅仅一次转发调用？只是转发 → 合并或删除。
5. **尺寸与深度测试**：契约一屏讲不完、公开操作多到需要目录，先审视拆分；小接口、大实现是深模块，接口复杂度接近实现复杂度是浅模块；接口极小但行为也极简单，是透传。
6. **重叠测试**：同一业务能力是否被两个模块同时拥有？同一业务规则是否在两处实现？同一业务数据是否有两个写入口？任一为是，就是业务重叠，必须消除。

**透传模块的例外**：防腐层、适配器、仓储可以薄，但其价值是隔离外部模型、稳定契约或封装访问策略；它们不算业务模块。纯业务转发没有这个价值，应合并或删除。

**业务重叠的处理顺序**：同能力且同变化原因 → 合并；能力混装 → 按能力重切；共享业务规则 → 抽领域服务；共享用例编排 → 上提到整合层。处理完在能力所有权矩阵中登记唯一 owner，不留两个 owner。

产出：候选模块卡、能力所有权矩阵、拆分/合并决策（含被否决的方案与理由）。

### 第 3 步：分层与依赖

按“离业务的距离”自下而上分三层。层是依赖方向的声明，不是目录装饰。

| 层 | 使命 | 允许 | 禁止 | 稳定性 |
|---|---|---|---|---|
| **L0 基础设施** | 把技术细节与外部世界隔离 | 数据库/ORM、HTTP/MQ 客户端、缓存、配置、日志指标、防腐层、外部适配器 | 业务规则、用例编排、把 SDK/ORM 类型泄漏到上层契约 | 低（易变，被隔离） |
| **L1 领域** | 承载业务规则与不变量 | 实体、值对象、领域服务、仓储/网关端口、领域事件契约 | 框架/ORM/SDK 类型、直接 I/O、跨模块用例编排、依赖 L2 | 高（稳定，扇入大） |
| **L2 整合** | 用例编排与组装 | 用例编排、事务边界、取数/转换/拼装、API/消费者、组合根、冷热路径协调 | 业务规则、裸 SQL/HTTP、第三方模型直接进入领域 | 中（随用例变化） |

**依赖规则**：

1. **调用方向**：L2 调用 L1 契约；L1 调用自己定义的端口；L0 实现端口，由组合根注入。L0 不调用 L1/L2 的业务代码，L1 不调用 L2。禁止反向调用，禁止循环依赖。
2. **源码依赖方向**：L0 → L1 端口（实现），L2 → L1 契约；L1 只依赖自己的端口与值类型。除组合根外，任何模块不得 import L0 的具体类型。这样“调用向下”与“依赖指向稳定”同时成立，不把依赖倒置误读成领域层依赖 ORM/HTTP。
3. **同层不相认**：同层模块禁止横向互调。共享数据下沉为数据服务（L1 基础子层或 L0 数据适配器），共享编排上提 L2，共享业务规则抽 L1 领域服务或合并。需要时把 L1 分为 L1a 领域基础（数据服务、共享领域服务、值对象）与 L1b 领域能力（业务模块）：只允许 L1b → L1a，反向禁止，L1a 之间不互调。数据服务不是同层兄弟，而是所有写入口的下沉点。L2 之间需要共享编排时，合并为一个用例模块，或把可复用部分下沉 L1，仍禁止横向调用；L0 的通用技术库可被同层适配器复用，但不得含业务语义，也不得反向依赖 L1/L2。
4. **事件不是反向调用**：发布者只依赖事件契约/端口，不依赖订阅者；订阅者依赖事件契约。事件契约归发布方或共享内核，变更需版本化。这样领域可以发事件，但不会反向调用整合层。
5. **扇出受限**：扇出 = 一个模块直接依赖的下层模块数（同步 + 异步，同一被调模块的多个契约按 1 计）。排除标准库、日志/指标/配置等横切工具、纯值类型。硬上限 8，目标 3–5；热路径上的模块扇出还应更紧：≤5，优先 ≤3。超限说明它在越权编排：按能力拆分、插入有业务价值的聚合模块，或把编排上提到 L2。不允许加一个透传聚合层来“消数字”。
6. **扇入求大**：扇入 = 直接依赖该模块的上层模块数，不设上限，越大越好；扇入越大的模块契约必须越稳定、改动越谨慎。1–2 为局部，3–5 为共享，6+ 视为平台级：必须契约评审、兼容性测试、废弃策略。
7. **依赖指向稳定**：优先依赖扇入大、变更频率低、契约抽象的一方。稳定模块若必须依赖易变细节，在稳定侧定义端口，由 L0 实现（依赖倒置）。不得让稳定模块直接依赖易变的具体实现。
8. **防腐隔离**：第三方/遗留系统的模型跨边界必须经过 L0 的防腐层。防腐层负责模型翻译、错误映射、超时/重试/鉴权/限流；我方契约不出现外部类型。防腐层要有契约测试和测试替身。稳定且 trivial 的标准库依赖不必包防腐层。
9. **装配集中**：每个可部署单元只有一个组合根，位于 L2/启动层；由它读取类型化配置、选择实现、注入依赖。模块内部禁止用环境分支挑选实现，禁止 service locator。
10. **编排三分**：通用编排原语（并发/串行/fan-in/fan-out/超时/补偿）在 L0，不含业务名；流程定义（这条价值流经过哪些组件、失败怎么办）归 L2 用例模块；单域内的顺序调用由该域顶层用例组件承担，不引入框架。跨域调用的唯一合法位置是 L2 编排，不得在 L0 里写业务顺序。
11. **共享技术组件在 L0**：日志、配置、主题、文件工具等横向共享放最底层，可被所有层调用；不得含业务语义，也不得反向依赖 L1/L2。共享层不是第二个领域层。

产出：分层模块地图、依赖矩阵、循环与扇出检查结果、防腐层清单、组合根位置。

依赖矩阵至少包含：

| 调用方 | 被调方 | 契约 | 方式（同步/异步/事件） | 路径（热/冷） | 失败处理 | 备注 |
|---|---|---|---|---|---|---|

同时列出**禁止边**：例如 L1 → L0 具体类型、L1 → L2、同层横调、第三方类型进入契约。

### 第 4 步：设计契约

契约先行：先定接口与类型，再写实现。契约冻结后才写实现；实现可以演进，契约变更必须版本化并给迁移路径。

**契约卡**（模板见第五节）至少写清：

- 签名：输入/输出只用我方稳定类型；
- 不变量：前置条件、后置条件、始终成立的规则；
- 错误模式：错误类型、触发条件、是否可重试、调用方应如何应对；
- 热路径/跨进程契约再补：幂等、顺序、并发、超时/取消/背压、一致性/可见性、版本/废弃。

**最小接口**：

- 公开成员能少则少，每个新增公开成员都要给出理由；能藏进实现的一律不暴露。
- 暴露能力，不暴露数据；不提供泄漏内部状态的 getter；不设计 `execute/handle/manager` 这类万能入口。
- 契约里只出现稳定概念。存储 schema、传输协议、第三方 SDK、序列化格式、重试策略、厂商选择都属于易变决策，不得进入契约。
- 契约宽度按调用方实际需要裁剪，不把下游 API 原样搬上来。

**接口即测试面**：

- 测试只通过契约进行。契约测试就是模块的验收测试，覆盖成功、失败、边界、不变量、并发/幂等语义。
- 想绕过契约测内部，先改模块形状：行为不可观察 → 增加契约级可观察行为；模块太粗 → 抽出协作者；只是验证实现细节 → 删除或改写该测试。
- 内部单元测试可以存在，但不能替代契约测试，也不能成为跨模块集成面。

**深模块与尺寸**：

- 深模块 = 小接口、大实现；接口复杂度应显著小于实现复杂度，调用方不需要知道内部步骤就能正确使用。
- 接口复杂度接近实现复杂度 = 浅模块：继续隐藏，或与相邻模块合并。
- 接口极小但行为也极简单 = 透传：合并或删除；技术边界模块例外。

**能力 ID 与入口符号**：契约上的每个公开操作用稳定 ID 引用（`CMP-xxx#op`）；场景与测试只引用 ID，不写文件行号。入口写成 `CMP-xxx/file#symbol`，由脚本校验符号存在。契约里写清性能与并发要求；写不出测量方法的阈值不许写，标 `none` 并说明。

**契约变更**：新增优先做成兼容扩展；破坏性变更必须新版本 + 迁移 + 废弃周期；热路径契约的破坏性变更按 P1 处理。

产出：契约卡清单、契约测试清单、兼容性/废弃说明。

### 第 5 步：冷热路径

每条用例/操作都要标注热或冷；混合路径在契约边界拆开，不内联。

- **热路径**：同步、关键用户旅程、高频、低延迟、失败对用户可见。例：核心请求处理、关键读写、实时事件处理。
- **冷路径**：异步、批量、后台管理、报表、迁移、恢复、补偿、审计；可延迟、可重试、可暂停。
- 不设第三类“温路径”。确实需要中间态时，明确它按热路径的失败语义还是冷路径的延迟语义处理，不能含糊。

| 维度 | 热路径 | 冷路径 |
|---|---|---|
| 触发 | 同步请求/实时事件 | 异步/批量/后台/恢复 |
| 目标 | 严格延迟与可用性 | 吞吐、完成时间、可延迟 |
| 依赖 | 最小同步依赖，≤3–5 | 可多、可异步 |
| 失败 | fail fast、降级、限流/泄载 | 退避重试、DLQ、重放 |
| 资源 | 专用线程池/队列/连接池/锁 | 独立资源，可暂停/限流 |
| 一致性 | 强/本地/读己之写 | 最终一致，写明最大延迟 |
| 变更 | 严格兼容 + 压测 | 可快迭代，但契约仍版本化 |
| 观测 | 延迟、错误率、饱和度 | 积压、延迟、重试、失败 |

**热路径规则**：

- 只保留必要的同步依赖；整条热路径的同步跨模块调用建议 ≤5，优先 ≤3；单个模块的扇出另受第 3 步约束。每个同步依赖都是一个失败点。
- 审计、通知、统计、报表、索引重建等冷活不得内联；用事件/outbox/异步移出。
- 显式超时、取消、背压、有界队列；失败快速返回或降级，不做无界重试。
- 不与冷路径共享线程池、队列、连接池、锁、事务；冷路径可被暂停或限流，不能拖垮热路径。
- 重试必须配幂等；错误模式区分可重试/不可重试；跨模块不放大事务，用 outbox/saga。
- 缓存只在有测量证据时引入；缓存是派生状态，必须有失效、陈旧度、击穿保护说明。
- 热路径的契约变更与架构变更需要更强兼容性审查和压测；架构级变更按 P1。

**冷路径规则**：

- 异步/事件驱动；消费者幂等、去重、退避重试、死信、重放、checkpoint。
- 最终一致；写明最大延迟与投影新鲜度；读取投影的一方要知道自己读的是投影。
- 独立部署/扩缩容；冷路径失败不阻塞热路径。
- 冷路径可以慢而周全，但契约、版本、观测仍不可省。

**路径卡**（模板见第五节）必须写：触发与频率、SLA、经过的模块与契约、同步依赖数、失败与降级、超时/重试/幂等/背压、资源隔离、一致性/最大延迟、观测指标。

产出：冷热路径清单、路径卡、资源隔离矩阵、观测计划。

### 第 6 步：装配、复用与状态

**组合优于继承**：继承只在框架强制要求时使用；其余一律组合 + 接缝（接口、端口、函数值）。接缝是“不改模块就能替换行为”的位置；没有接缝的复用是复制。

**复用归位**：

- 同一逻辑第二次出现即触发归位判定，逐问回答再决定抽不抽：
  1. **是同一业务语义吗？** 列出两处的差异；差异能用参数或配置表达、且不引入语义分支的，才算同一语义。
  2. **会因同一个业务原因一起变化吗？** 变化原因不同的「形似」不抽——将来各自要改的，抽了反而耦合。
  3. **抽出的公共契约会稳定吗？** 契约若必须把两处的差异全暴露成参数，说明不是同一逻辑。
  三问皆「是」→ 抽到模块库；任一「否」→ 不抽，在两处记录不抽取的理由，禁止无理由复制。
- 放哪层按“离业务的距离”判断：通用技术工具 → L0；业务规则/值对象 → L1；用例编排/取数转换拼装 → L2。
- 禁止 `common/utils` 成为业务规则垃圾场；共享内核要小而稳定，扇入大者按平台级契约管理。

**无胶水**：取数、转换、编排只住在 L2 整合模块里。调用方出现“取 A、取 B、拼装、再调 C”的拼装逻辑，一律处理：数据访问/转换下沉到数据或领域服务；用例编排上提到 L2；重复出现则归位到模块库。不允许留在调用方。

**装配集中**：依赖的选择与注入只发生在组合根；模块内部禁止用环境分支挑选实现。配置在组合根读取、校验、类型化后传入；模块接收的是明确依赖，不是全局容器。测试通过测试组合根或契约替身注入。

**模块无状态**：

- 请求级状态由 context 显式携带。context 只放请求级横切事实（租户、用户、截止时间、取消、trace 等），不放业务状态，也不拿 context 当 service locator。
- 模块级可变业务状态禁止；模块重启后、并发双跑时行为一致。
- 跨实例正确性靠幂等键、乐观并发、唯一约束、必要的分布式协调；本地锁不足以支撑双跑。
- 缓存是派生状态，必须有失效与陈旧度说明；连接池/线程池属于基础设施状态，允许存在但必须封装，且冷热隔离。

**数据单家**：

- 共享业务数据只允许一个写入口，即数据服务模块；其他模块通过契约写，不直连存储。
- 读优先走所有者契约；只读投影/副本必须登记延迟、失效规则和读取方，不能成为第二真相。
- 迁移归数据服务所有；schema 变更按 P 级处理。
- 事务边界在 L2 用例；数据服务提供事务性操作；跨模块分布式事务用 outbox/saga，不放大本地事务。

产出：组合根与装配说明、复用登记、数据所有权矩阵、状态/并发说明。

### 第 7 步：为每个模块写验证计划

每个模块必须自带验证计划；没有验证计划的模块不算完成。验证计划要能回答五个问题：

1. 契约的每个不变量，由哪个测试证明？
2. 每个错误模式，由哪个测试触发？
3. 热路径的依赖预算、超时、降级，由哪个测试/压测证明？
4. 冷路径的积压、重试、重放，由哪个测试证明？
5. 依赖方向、同层禁止、扇出上限、契约无泄漏，由哪个架构测试守住？

验证矩阵至少覆盖：

| 模块 | 契约测试 | 规则/不变量 | 失败/降级 | 冷热/隔离 | 架构约束 | 数据/迁移 | 观测 |
|---|---|---|---|---|---|---|---|

- **契约测试**：成功、失败、边界、不变量、并发/幂等；只走公开契约。
- **规则测试**：每个业务不变量至少一个用例；适合时用表驱动或属性测试。
- **失败测试**：依赖超时/报错/部分失败；重试、幂等、降级、补偿。
- **冷热测试**：热路径延迟/错误/饱和；冷路径积压/重放；冷负载不影响热路径。
- **架构测试**：import 规则、无环、同层不互调、扇出阈值、契约无框架/SDK/ORM 类型、防腐层边界。
- **数据测试**：单写入口、迁移、并发、一致性。
- **观测**：指标、日志、trace 覆盖契约与路径；热路径有延迟/错误/饱和告警，冷路径有积压/延迟/失败告警。

自动化优先；只有业务价值、重叠、定级这类判断留给人。CI 至少守住契约测试、架构测试、热路径冒烟、迁移测试。

产出：模块 × 测试类型矩阵、CI 门禁清单。

### 第 8 步：评审、裁决与输出架构规格

用场景走查，不只读图：

1. **正常流程**：走一条端到端用例，检查契约、数据所有权、热路径。
2. **失败流程**：每个跨边界依赖超时/报错/部分失败时，谁重试、谁补偿、谁上报；热路径如何降级。
3. **扩展场景**：新增一种渠道/格式/规则，是否只改一个模块和契约？不是则边界错了。
4. **峰值 + 冷路径叠加**：热路径高峰时跑批/重建/报表，资源是否隔离，热路径是否被拖垮。
5. **重启/双跑**：两个实例并发、处理中途重启，状态是否一致；幂等与并发控制是否足够。
6. **第三方变更**：外部模型/协议变更，是否只改防腐层，我方契约不动。
7. **删除测试**：逐个删模块，复杂度消失（透传）还是集中（真边界）；消失的合并/删除。

每条发现按四档裁决。档位与 P0–P3 定级正交：定级在动手前决定设计重量与人工门；裁决在冻结/合并前决定每条发现怎么处置。两者不要合成一个刻度。

- **Blocker**：数据丢失、默认行为错误、不可逆、契约自相矛盾，冻结后再修就是 breaking change。证据：可执行复现或测试映射 + 代码位置；「我觉得有问题」不算，无证据自动降档。动作：清零才能冻结/合并，落回归测试与 result.md。
- **Decision now**：两种行为都说得通，但冻结后再改就是 breaking change。证据：当前行为验证 + 选项与代价 + 受影响调用方。动作：定，同时落文档（契约卡 / `history/decisions/`）与 pinning test；只写决定不算。
- **Verified sound**：已查且确认无问题的区域。证据：查了什么、怎么查（命令 / 测试 / 对照）、结果如何；禁止写「其余正常」。动作：不改，禁止顺手优化，落 review.md 正面清单。
- **Hold**：以后改不 breaking（不阻塞但该修），或超出本次范围。证据：为什么不阻塞或延后安全；本次仍须决定的那一件摘出来。动作：转待办 / `plan/open-questions.md` / 下一工序，不进本次 diff。

按定级裁剪：P1 四档齐全，冻结前做一次 breaking change 审查，只问一句「哪些问题发布后再修就变成 breaking change」；P2 至少 blocker、decision now、verified sound；P3 不写评审文件，commit message 一行裁决，无 blocker 写「无」。

评审结论四选一：**通过 / 有条件通过 / 重新设计 / 阻塞**；选「有条件通过」必须标明条件属于哪一档。记录决策、反对意见、开放问题与 owner。P1 必须有人确认记录；P2 必须有人最终确认；P3 自动测试通过即可；P0 只输出阻塞简报。

P1 的人参与分两次：第一次带候选模块图、契约草案、关键取舍与开放问题，先定边界与契约；第二次带完整规格与走查结果，做最终确认。不要在第一次就丢一份完整文档让人从头读。

产出：完整架构规格（P1）或影响规格（P2）或变更说明（P3）或阻塞简报（P0）。

## 四、评审清单

| 维度 | 必须通过（证据） | 失败信号 |
|---|---|---|
| **模块** | 一句话说清负责/不负责；业务价值成立；能力唯一 owner；删除测试通过；尺寸与深度合理 | 职责含“和/以及”；机械转发；两个模块同一能力；契约一屏讲不完；删掉后复杂度消失 |

| **状态/数据** | context 携带请求状态；重启/双跑一致；单写入口；无直连存储；事务边界清楚 | 模块级可变业务状态；双跑不一致；多写入口；跨模块直连 DB |
| **冷热** | 路径卡齐全；热路径 ≤5 依赖；冷热资源隔离；热失败语义；冷幂等/重放；观测 | 热路径内联审计/通知/统计；冷批拖垮热路径；共享队列/锁；无降级 |
| **验证/分级** | 每模块验证计划；契约测试；架构测试；P 级与确认记录 | 模块无验证；只测 happy path；无架构测试；级别与触发项不符；P1 未确认就编码 |

## 六、与其他 skill 的协作

- 先走 **design-before-coding** 的业务复述、现状盘点、模式选择与场景走查；本 skill 在其上补架构规格。若只做架构评审，可跳过模式选择，但业务能力盘点与现状依赖图不能省。同一修改只画一张地图：本 skill 的分层模块地图就是组件地图的架构细化，不两图并行维护。
- 编码执行、验收与提交纪律遵循 **dev-execution-spec**；本 skill 定下的改动级别与人工确认门是它动工前的前置核对——P1 未确认不编码，P2 未确认不合并。
- 架构规格、模块卡、依赖矩阵、契约卡属于现行真相，按 **doc-layout-spec** 落到 `design/architecture.md` 或 `design/<module>/spec.md`；评审过程、候选方案、被否决理由落到 `works/<工序>/`；定稿决策落到 `history/decisions/`；踩过的坑落到 `history/pitfalls.md`。
- 冲突时：文档放哪里听 doc-layout-spec；通用设计流程听 design-before-coding；架构内容判据听本 skill；动手到交付的执行纪律听 dev-execution-spec。

## 七、完成定义

- **P3**：变更说明 + 自动化测试通过；未触碰任何架构触发项。
- **P2**：影响规格 + 契约 diff + 迁移/回滚 + 测试计划 + 人最终确认记录。
- **P1**：模块地图 + 依赖矩阵 + 契约卡 + 冷热路径卡 + 数据所有权矩阵 + 逐模块验证计划 + 人参与切分/契约评审 + 最终确认记录；无环、无同层横调、扇出在预算内、每个模块有业务价值与验证计划、无业务重叠、冷热资源隔离。
- **P0**：阻塞简报，含已知/未知、选项与代价、需要人决策的问题；不写实现代码。
- 结构性修改后同步更新模块地图、依赖矩阵与契约卡；过期地图比没有地图更危险。
