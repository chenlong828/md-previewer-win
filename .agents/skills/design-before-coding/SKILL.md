# 先设计，后编码

面对开发任务，第一动作不是生成代码，而是完成一次业务与逻辑层面的设计拆解。代码只是设计的表达；结构混乱几乎总是跳过设计直接堆代码的结果。设计的目标不是产出完美图纸，而是让每次功能扩展与变更都有明确、局部的落点，让复杂度的增长始终可见、可控。

本 skill 中的「组件」泛指有明确边界的软件单元——模块、包、服务或类，按所在语言与系统的粒度对应。

## 核心原则

- **职责单一，能一句话命名**。讲不清一个组件做什么，就是还没拆对；要靠「管理器」「助手」「公共」这类词才能概括的组件，职责多半已经混合。
- **高内聚**：因同一理由变化的代码放在一起。可执行的判据是：改变一条业务规则，只需要修改一个组件。
- **松耦合**：组件之间只通过显式契约（接口、事件、消息、数据结构）交互；契约上传递的信息越少越好；依赖指向稳定、不易变化的一侧。
- **数据只有一个权威来源**：每份数据写明谁是真源，其余副本都是投影或缓存，并写明各自的刷新与失效规则。写入口唯一、数据服务模块的架构判据见 arch-design-spec（数据单家）。
- **路径分离**：让每类关注点有自己的直线。实现与验证分离——校验放在边界入口与独立的对账环节，不散落成主逻辑里的断言；主路径与分路径分离——正常流程直线可读，分叉向外；常用路径与偶发路径分岔——高频代码与低频代码（恢复、补偿、降级）各自成路，偶发路径可以慢而周全、独立加固，失败不拖垮常用路径，超时与取消是显式的状态迁移而不是内联分支。
- **为变化而设计**：先识别业务上最可能变化的轴（渠道、格式、规则、流程步骤、规模），再把每个变化轴隔离到一个组件边界之后。
- **复杂度有预算**：每引入一层抽象或一个模式，都要说清它换来了什么；说不清收益的抽象应当删除。

## 设计优先级：冲突时的裁决顺序

四项关注点发生冲突时，按此顺序裁决。这是「谁让步」的默认答案，不是开发排期：功能排最后不是不重要，而是功能必须穿过前三项修好的路径交付。低序位的机制是高序位工作的前提——契约化让上层修订可行，路径分离让整体优化可行。

1. **维护性（第一）**：模块化与契约化。软件的大半生命周期是被修改，维护性是唯一有复利效应的质量属性；削弱边界或契约的捷径（绕过接口直连、用标志位代替新契约、为省事合并组件）默认拒绝。
2. **运行稳定性（第二）**：靠路径分离取得——实现与验证分离、主路径与分路径分离、常用路径与偶发路径分岔（见核心原则）；常用路径的故障面最小，偶发路径独立加固、失败不拖垮常用路径。
3. **性能（第三）**：区分性能要求与性能优化。要求在设计期作为契约目标写入修改方案；优化是例外驱动的活动——实测不足才沿完整执行路径整体进行，不为臆想的性能牺牲边界，不用散落各处的局部技巧预付复杂度。
4. **功能实现（第四）**：功能经由结构交付。新功能与既有契约不合时，修订上层设计与契约（评估全局影响），或在边界处开正交分岔；不在下层绕行（判据见第七步）。

## 工作流

### 第一步：从需求卡与场景节点开始

不重新问一遍目标。先读需求卡（`REQ-xxxx`）与受影响场景（`SCN-xxxx`）：卡上的场景叙述、价值、非目标、影响场景就是本次的三件套（定义处见 req-scenario-spec）；缺项先问，不自行假设。

确认三件事：本次改的是哪个场景的哪一条断言；是否只动一个组件；失败路径在场景的运行序里怎么走。正常流程与失败路径以场景卡为准，不另写一份。

区分业务规则（领域固有）与技术需求（实现引入），二者不放进同一个组件；哪些方面将来最可能变化，这个判断决定后续所有结构选择。

### 第二步：盘点现状

大多数任务发生在既有系统里：

1. 读入口与主要调用链，画出现状：组件、层次、依赖方向、数据流。
2. 标出本次修改的落点与波及面（受影响的组件范围）：哪些组件必须改、哪些契约会变、哪些必须保持不变（兼容性承诺）。
3. 先理解既有结构为什么长成这样，再判断它是合理约束还是待偿还的债务；不基于现状地图的理想设计，会在落地时与既有结构冲突。

### 第三步：拆解组件

1. 按职责拆，不按技术分层或文件大小拆。
2. 每个组件写三行：一句话职责；它拥有什么数据（持久化状态归谁）；它依赖谁。
3. 用两个问题自检：业务规则变化时要改几个组件？答案应为一。这个组件能脱离上下文独立读懂吗？答案应为能。
4. 拆不动（职责纠缠、共享状态过多、循环依赖）本身就是重要发现，要作为设计风险明确提出，而不是绕过去。

### 第四步：分层，画组件地图

1. 层次就是依赖方向的声明：上层使用下层，下层不知道上层；依赖禁止成环。
2. 第三方模块与自身主要逻辑交织时，中间必须有一个领域适配器：接口用自己领域的词汇和类型定义，宽度按领域实际用到的操作裁剪，第三方的类型与错误不出现在接口表面。这样外部升级只改适配器一处；迁移时新旧实现并存于同一接口之后，切换而非重写；其余组件可脱离第三方独立测试。轻量稳定的工具依赖不必包适配器；适配器只服务一个领域边界，不堆放无关操作。
3. 产出一幅组件地图（文本清单或图）：层次、每个组件的一句话职责、组件之间的契约。地图是交付物的一部分，每次结构性修改后同步更新。
4. 修改任何代码之前，先在地图上定位：改动落在哪些组件、哪些契约要动、哪些组件完全不受影响。定位不清就不动手；在过期的地图上继续堆功能，是代码混乱的最大来源。

### 第五步：为边界选择模式

引入设计模式（门面、适配器、仓储、状态机、策略、发布-订阅等）与技术方案模式，只有一个正当理由：预期中的变化正好落在该模式预留的扩展点上。每次选择逐条回答：

1. 这个模式为哪类未来变化留了口子？该变化有多大可能发生、何时发生？答不上来就不引入。
2. 模式的成本（间接层次、新概念、样板代码）与它隔离的变化相称吗？一次性逻辑不需要策略模式；按配置二选一的开关，用条件分支就够了。
3. 语言、平台或既有依赖里有没有现成机制？有就用现成的，不自己搭建。
4. 用满足当前需求与已知变化的最简结构；不为想象中的需求预付复杂度，但在组件边界处保留低成本的替换点：对外暴露自己定义的接口，实现细节藏在接口后面。
5. 记录每次选择：解决的问题、预期的变化、被否决的替代方案及否决理由。这段记录防止后来者（包括未来的自己）把已经否决的路再走一遍。

### 第六步：用场景走查设计

编码之前，在纸面上推演：

1. 一个正常流程、一个失败流程：每个跨边界的调用失败时，谁负责重试、回滚或上报；每份流转中的数据由谁持有、由谁释放。
2. 三条路径分离是否成立：验证没有混入实现，主路径直线可读，偶发路径（超时、取消、恢复）是显式分岔的状态迁移而不是内联分支。
3. 一个未来的扩展场景（例如新增一种渠道、格式或规则）：确认扩展正好落在预留的扩展点上，不破坏任何现有契约。
4. 走查失败就回到第三步重新拆解；带着未通过走查的设计进入编码，问题会在实现中途暴露，返工成本更高。

### 第七步：输出组件级修改方案，然后编码

设计或变更定稿后、动手编码前，先输出一份组件与模块级别的修改方案，经确认后再编码。方案除了前几步已产出的组件清单、层次与模式选择，必须写清三类「调整」：

1. **外部契约调整**：对外接口、事件、消息格式、配置项、持久化数据结构的新增、变更与废弃；不兼容变更写明迁移方式。
2. **组件间关系调整**：
   - 调用关系：谁调用谁、经过哪个契约（接口、事件、消息）、方向如何；新增与切断的调用边都要列出。
   - 从属关系：组件与数据的所有权——谁创建、谁持有、谁销毁，生命周期由谁管理。
   - 数量对应关系（基数）：组件实例与数据之间是 1:1、1:N 还是 M:N，例如一个会话持有 N 个任务、M 个订阅者接收 N 类事件。基数变化往往意味着隐藏的重新设计，必须显式写明。
3. **修改点与波及面**：要改的组件、要动的契约、明确不受影响的组件（兼容性承诺），以及未决问题。

新功能与既有契约不合时，修改方案必须二选一：修订上层设计与契约，写明全局影响与迁移路径；或在组件边界处新开一条正交的独立路径。下层加特例与绕行不是选项。判据：契约无法自然表达这个功能、要扭曲才能塞进去的，修订契约；功能本质是与主路径正交的偶发路径的，开新路径。

涉及性能的设计（对吞吐、延迟、容量有要求的路径），修改方案必须再补充四项：

4. **并发模型**：哪些操作并行、哪些因共享状态必须串行、并发度上限、队列与缓冲区设在哪。
5. **数据面与控制面的性能要求**：数据面（业务数据的实际处理路径）与控制面（配置、协调、状态汇报路径）分别给出吞吐、延迟、容量目标；两者要求通常相差数量级，不得共享同一个队列、锁或事务。
6. **事务边界**：每个事务覆盖哪些组件与数据；跨多次外部调用或长时间持有的流程，用意图记录加补偿动作收尾，不放大事务。
7. **锁的关系**：每把锁保护什么数据、粒度多粗、持有多久、按什么顺序获取（全系统一致的获取顺序防死锁）；数据面与控制面分开加锁，热路径不与冷路径竞争同一把锁。

方案里的运行序写进场景目录，契约细节写进组件规格；同一事实不写两遍（放置见 doc-layout-spec）。

编码期间发现方案与现实冲突：停下，先更新方案，再继续；不允许代码悄悄偏离方案。

修改方案、设计简报等过程文件的存放与归档遵循 doc-layout-spec skill：它们落在进行中需求的工序工作区，组件地图与定稿规格落在现行真相层。

改动触碰模块切分/合并、公共契约、schema、数据所有权或热路径时，模块切分、分层依赖、契约设计与改动定级遵循 arch-design-spec skill：它管架构规格层，定 P0–P3 改动级别并设人工确认门。

需求、场景与任务拆分遵循 req-scenario-spec skill：需求卡与场景卡是设计输入，任务按组件与场景拆分。

编码执行、验收与提交的纪律遵循 dev-execution-spec skill：它管动手到交付这一段——diff 聚焦、修 bug 先最小复现、测试验证具体业务结果、交付前 git 检查点；本 skill 定下的验收三件套在那里逐条核对收口。

## 按任务规模裁剪流程

- **小改动**（缺陷修复、局部调整）：一到两段话完成问题复述、修改点定位与方案说明即可，不套全流程；但只要动了外部契约或组件间关系，修改说明里必须点明这两点。
- **中等任务**（新功能、新模块）：走完整工作流，修改方案控制在几十行内。
- **大任务**（子系统设计、多方案权衡）：工作流全程，另出独立设计文档；组件地图、修改方案与模式选择记录构成文档主体。
流程的重量必须与任务的波及面相称：对小任务套重流程，与对大任务跳过设计，是同一种失败。
改动级别（P0–P3）由 arch-design-spec 判定，决定架构规格的深度与人工确认门；本节的任务规模只决定本工作流的裁剪。两把尺子各量各的，结论不一致时按更重的一档执行。

## 混乱的信号

出现任何一条，先停下重新拆解，而不是继续堆代码：

- 组件说不清单一职责，名字要靠「管理器」「助手」「公共」撑着。
- 改一条业务规则，需要跨多个组件同步修改。
- 两个组件互相知道对方的内部数据结构。
- 同一份数据存在两个都自称权威的来源。
- 新增一个小功能，必须先读懂大量与它无关的代码。
- 代码里模式的名字比业务的名字还多：模式在为自己服务，而不是为业务服务。
- 第三方库的类型出现在自己领域接口的签名或错误里。
- 偶发逻辑（重试、恢复、降级）以标志位内联在主路径上，而不是独立分岔。
- 没有测量证据的性能补丁：跨边界内联、防御性缓存、为省一次调用合并组件。
- 新功能靠下层特例塞进系统，上层契约原封不动。
