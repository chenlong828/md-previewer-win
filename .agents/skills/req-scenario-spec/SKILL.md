# 需求到任务：卡、树、场景、任务

需求用卡承接，分析用树定位，交付按场景拆任务，一个任务一个对话。本 skill 只定这条链路；组件、分层、契约归 arch-design-spec，文档放哪归 doc-layout-spec。

## 一、链路

```
需求卡 REQ ──影响分析──▶ 场景 SCN ──任务拆分──▶ 任务 T（一个对话）──▶ commit
   │                        │
   └─ 类型/状态             └─ 入口/运行序/引用/测试
```

- 需求卡在 `requirements/`，场景在 `design/scenarios/`，任务序列在 `works/<工序>/brief.md`。
- 标识：`REQ-0001`、`SCN-0001`、`CMP-xxx`、`T-xxxx-01`、`W-日期-短名`，稳定不复用。
- 引用一律用 ID，不写文件行号；解析失败按红灯处理。

## 二、需求卡

**一卡一结果**。判据：删掉这张卡，用户会感知到少了哪一个动作；两个动作拆两张卡。不设父子卡，大主题用 roadmap 的批次分组。

| 字段 | 内容 |
|---|---|
| ID | `REQ-0001` |
| 类型 | `feature` / `quality`；`debt` / `doc` 不建卡，走旁路 |
| 场景叙述 | 谁、在什么情况下、完成什么动作、得到什么结果 |
| 价值 | 不做的后果（比“有什么好处”更难编） |
| 非目标 | 本次明确不做什么 |
| 约束 | 不得引入依赖、兼容性、性能等横切要求 |
| 影响场景 | `SCN-xxxx` 列表，可含“待新建” |
| 澄清记录 | 时间 + 问题 + 结论，追加不覆盖 |
| 状态 | `draft → accepted → delivered`；或 `superseded` / `dropped` |

**澄清**：需求模糊时先问，问清场景、价值、非目标、影响面四件事；一次问 2–3 个并给选项，不挤牙膏。问不出结果的记入 `plan/open-questions.md`，卡留 `draft`。

**accepted 判据**：场景叙述可判定、非目标明确、影响场景已识别。不要求场景已建好。

**验收归属**：需求不另立测试。验收 = 影响场景全部 `verified` + 约束未被违反。

## 三、业务功能树

三层：`领域 / 价值流 / 场景`，默认不加第四层。同层同质：领域都是业务能力，价值流都是流程，场景都是旅程。

- 价值流按**要解决的问题**命名（响应性、可移植性），不按手段命名（并行、线程池）。
- 第四层门：该子流程有自己的流程定义与独立场景集合；否则它只是场景里的一个步骤。
- 加层、改层、改领域归属属于结构决策：给 ≥2 个候选与否决理由，人确认后落。

**DFX 域**：与业务域并列，标 `kind: dfx`。六类固定：响应性、可靠性、安全性、可维护性、可移植性、可观测性。叶子分三桶：

| 桶 | 放哪 | 怎么验 |
|---|---|---|
| 附着预算 | 挂在业务场景上的附加断言 | 场景测试 + 基准 |
| 守门项 | DFX 域的 guard | 架构测试/基准，常驻 CI |
| 开发者旅程 | DFX 域场景 | 3 正 1 反 |

DFX 条目必须有阈值 + 守门手段 + owner，缺一就走旁路，不进树。能由脚本稳定判定的写成 guard，不写叙事。

## 四、场景卡

一个场景一个目录，一份 `scenario.md`。

| 元素 | 内容 | 可为 none 的情况 |
|---|---|---|
| 入口 | `CMP-xxx/file#symbol`，可多个 | 纯检查型场景（用命令作入口） |
| 运行序 | 流程定义 ID + 组件序列 + 失败路径 | 不允许 |
| 不可变引用 | 上下游或外部契约，本次不得改 | 场景不依赖任何外部契约 |
| 测试 | 3 正例 + 1 反例；方案 + 可执行 ID | 不允许 |

**状态**：`draft`（四元素可缺）→ `designed`（运行序、引用、测试方案齐；入口可 miss）→ `verified`（四元素齐且测试 pass）。字段值 `present / missing / none`；`none` 必须写理由；`missing` 汇总成欠账清单。

**ID**：`SCN-0001`，稳定不透明；路径只定位，可随树调整。索引由工具生成，标 `generated`，不手改。

**verified 判据**：3+1 全 pass；`skip` 必须有替身（harness/像素探针/人工记录）并登记，否则最多 `designed`。

## 五、影响分析

需求 intake 时只读树 + 在卡上记影响场景（含待新建），不改 design。场景目录由工序的第一个 `design` 任务创建。

每个受影响场景写清：本次**新增或修改哪条断言**。只复用、不新增断言的场景，不能作为该需求的验收证据。

## 六、任务拆分

一个场景 = 多个任务；一个任务 = 一个对话 = 一次交付。

| 类型 | 改几个组件 | 出口 |
|---|---|---|
| `design` | 0 | 场景到 `designed` |
| `change` | 1 | 组件测试绿 + 场景不回归 + 组件规格更新 |
| `verify` | 0 | 场景测试可执行且绿 + 场景 `verified` + 需求状态更新 |

规则：

- **组件级 WIP=1**：一个组件同一时刻只允许一个在飞任务，其余排队。
- **装载清单**：brief 每个任务列出必读文件；单任务装载 ≤250k，单组件 ≤120k；超了拆任务或拆组件。
- **任务表**：`works/<工序>/brief.md` 维护 ID/类型/组件/状态/装载清单。
- **交接**：开工读 roadmap → 任务表 → 装载清单；收工更新状态 + 一句结论 + 未决问题。commit 只在任务完成时产生，绑定 `T-` 与 `SCN-`。
- 新增组件是 P1 结构决策，不在这条流里走。

## 七、旁路：技术债与文档

没有用户旅程的活直接建工序，brief 即锚点，不进 `requirements/`。改了架构或契约的，补 ADR 或组件规格；一次性优化不写进 DFX 树。

## 八、失败信号

- 一张卡里有两个可独立交付的结果。
- 一个场景里出现两个“结果”。
- 需求验收另立一套测试，与场景测试并存。
- 任务跨了两个组件还说是一个任务。
- 两个工序同时改一个组件。
- 场景标 `verified`，但有 skip 无替身。
- DFX 条目没有阈值或守门手段。

## 九、与其他 skill

- 组件、模块、分层、契约、预算 → arch-design-spec
- 动手前组件级设计、模式选择、走查 → design-before-coding
- 执行、验收、提交、模糊先问 → dev-execution-spec
- 放哪、frontmatter、归档 → doc-layout-spec

冲突时：拆分与链路听本 skill，结构听 arch，放置听 doc-layout，执行听 dev。
